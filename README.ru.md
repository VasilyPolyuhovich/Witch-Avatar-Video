# Witch Avatar Video

*Readme также доступен на: [English](README.md) | [Українська](README.uk.md)*

Генерирует короткие (5-15с) видео-флаеры "говорящей головы" вымышленного
персонажа — ведьмы/гадалки — для Instagram, из референсного фото и строки
русского текста: локальный синтез речи, затем GPU-под по требованию
рендерит видео с синхронизацией губ и сам себя завершает.

Полное обоснование дизайна: [`docs/2026-08-13-witch-avatar-video-design.md`](docs/2026-08-13-witch-avatar-video-design.md).
Журнал эмпирических находок/решений: [`docs/decisions.md`](docs/decisions.md).

## Как это работает

1. **Синтез речи выполняется локально**, на вашей машине — [Chatterbox
   Multilingual TTS](https://github.com/resemble-ai/chatterbox) превращает
   ваш русский текст в `.wav`, опционально клонируя голос из короткого
   референсного образца. На этом этапе GPU-под ещё не существует, поэтому
   неудачный текст или референсный клип ничего не стоят.
2. **GPU-под разворачивается на RunPod по требованию** ([EchoMimicV3-Flash](https://github.com/antgroup/echomimic_v3),
   диффузионная модель на базе Wan2.1-Fun), рендерит фото+аудио в видео, и
   под **всегда завершается после этого** — при успехе, ошибке или
   Ctrl-C — так что ничего никогда не остаётся работать и тарифицироваться
   случайно.
3. **Два независимых способа запуска**, оба обращаются к одним и тем же
   образам пода:
   - `scripts/generate_witch_video.py` — CLI-скрипт, запустите его и
     получите `.mp4` обратно.
   - **WebUI** (`webui/`) — небольшая защищённая паролем локальная
     веб-страница (ввести текст, загрузить фото, нажать Generate) для
     нетехнического использования.

## Предварительные требования

- **Python 3.10+** локально (разработано/протестировано на Apple Silicon,
  macOS).
- **Аккаунт RunPod** с настроенным биллингом ([runpod.io](https://runpod.io)) —
  именно он реально выполняет GPU-рендер. Типичная стоимость: **~$0.05-0.10
  за одно сгенерированное видео** (см. [Стоимость](#стоимость) ниже).
- **`ffmpeg`**, установленный локально (`brew install ffmpeg` на macOS) —
  используется для постобработки TTS-аудио.
- **Docker**, только если вам когда-либо понадобится пересобрать образы
  пода самостоятельно (не нужно для повседневного использования — образы
  уже собраны и опубликованы в GHCR через CI).

## Одноразовая настройка

### 1. Клонирование и установка

```bash
git clone <this-repo-url>
cd Witch-Avatar-Video
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

**Известная локальная проблема:** зависимость `chatterbox-tts` для
водяных знаков (`resemble-perth`) нуждается в устаревшем модуле
`pkg_resources`, который современный `setuptools` (начиная примерно с
версии 76) больше не поставляет. Если вы видите `TypeError: 'NoneType'
object is not callable` изнутри Chatterbox, выполните:

```bash
.venv/bin/pip install "setuptools==75.8.0"
```

(pip выведет предупреждение резолвера о том, что `torch` хочет более
новый `setuptools` — это просто предупреждение, не реальный конфликт;
torch работает нормально.) Смотрите `docs/decisions.md` / память проекта
за полной историей, если это продолжает повторяться.

### 2. Получение API-ключа RunPod и SSH-пары ключей

1. Создайте API-ключ на [runpod.io/console/user/settings](https://www.runpod.io/console/user/settings)
   и сохраните его в `~/.runpod-key-witch-video` (обычный текстовый
   файл, только сам ключ, без кавычек/проблем с переносом строки).
2. Сгенерируйте SSH-пару ключей, которой будут доверять поды RunPod:
   ```bash
   mkdir -p ~/.runpod/ssh
   ssh-keygen -t rsa -b 4096 -f ~/.runpod/ssh/runpodctl-witch-video-ssh-key -N ""
   ```
   (`scripts/pod_up.py` по умолчанию читает эти два пути — переопределите
   через переменные окружения `ACCOUNT_KEY_FILE` / `SSH_PUBKEY_FILE` /
   `SSH_PRIVKEY_FILE`, если храните их в другом месте.)

### 3. Настройка сетевого тома (одноразово, ~24ГБ весов модели)

Веса EchoMimicV3 (~24ГБ) живут на **сетевом томе** RunPod, а не запечены
в образ пода — том, будучи однажды заполненным, переиспользуется каждым
следующим рендером без повторной загрузки чего-либо.

1. Создайте сетевой том на 30ГБ через консоль RunPod (Storage → Network
   Volumes) в дата-центре с реальным (а не только глобально указанным)
   наличием карт ≥40ГБ — см. [Устранение неполадок](#устранение-неполадок)
   ниже о том, как проверить реальное наличие по конкретному дата-центру
   перед выбором, поскольку стандартный показ ранжирования GPU — это
   глобальный агрегат, который может вводить в заблуждение для деплоя,
   привязанного к тому. Запишите id тома. Дайте только что созданному
   тому несколько минут, прежде чем доверять любым отказам деплоя как
   "нет в наличии" — см. Устранение неполадок.
2. Разверните дешёвый временный под с этим томом, подключённым в
   `/workspace` (подойдёт любая небольшая GPU — этому шагу не нужны
   реальные вычисления, только смонтированный том):
   ```bash
   NETWORK_VOLUME_ID=<ваш-id-тома> MIN_VRAM=8 MAX_PRICE=0.2 \
     .venv/bin/python3 scripts/pod_up.py
   ```
3. Подключитесь по SSH к этому поду (команда выводит строку SSH),
   загрузите и запустите скрипт заполнения, затем завершите под:
   ```bash
   scp -P <port> -i ~/.runpod/ssh/runpodctl-witch-video-ssh-key \
     scripts/populate_echomimicv3_volume.sh root@<ip>:/root/
   ssh -p <port> -i ~/.runpod/ssh/runpodctl-witch-video-ssh-key root@<ip> \
     "chmod +x /root/populate_echomimicv3_volume.sh && /root/populate_echomimicv3_volume.sh"
   ```
   Ожидайте загрузку ~24ГБ, которая займёт несколько минут. Скрипт
   проверяет SHA256 каждого загруженного pickle-чекпоинта перед
   завершением.
4. Завершите временный под (через консоль RunPod или `podTerminate` через
   API) — не оставляйте его работающим.
5. Установите `DEFAULT_NETWORK_VOLUME_ID` в `scripts/pod_up.py` в id
   вашего тома (или экспортируйте `NETWORK_VOLUME_ID` при каждом запуске
   скрипта вместо жёсткого прописывания).

Это нужно сделать только один раз. Сами образы (`witch-avatar-echomimicv3`
и `witch-avatar-echomimicv3-webui`) уже публичны в GHCR и автоматически
пересобираются через CI при каждом изменении в `docker/echomimicv3*/` —
ручная сборка Docker не нужна для обычного использования.

## Использование

### CLI

```bash
.venv/bin/python3 scripts/generate_witch_video.py \
  --image assets/gadalka_portrait.jpg \
  --text "Добро пожаловать, дитя моё. Огонь свечи откроет тебе то, что скрыто во тьме." \
  --voice-sample assets/gadalka-voice-reference.wav \
  --output outputs/flyer.mp4
```

- `--voice-sample` опционален — опустите его, чтобы использовать
  встроенный голос Chatterbox по умолчанию вместо клонирования.
- `--dry-run` ранжирует доступные GPU и печатает, что произошло бы — без
  вызова TTS, без деплоя, без затрат. Используйте это для проверки
  цен/наличия GPU перед реальным запуском.
- `--tts-only` генерирует только локальный аудиофайл и останавливается —
  полезно для предпросмотра звучания текста перед тратой денег на под.
- `--max-price` / `--min-vram` переопределяют поиск GPU (значения по
  умолчанию: минимум 40ГБ, потолок $0.60/час — см.
  [Известные ограничения](#известные-ограничения)).
- Полный список флагов: `--help`.

Под **всегда** завершается в блоке `finally`, включая Ctrl-C или сбой
посреди рендера — вам никогда не должно понадобиться вручную очищать
под после CLI-запуска.

### WebUI

Запустите локальный бэкенд (он работает на вашей собственной машине, не
на RunPod — именно он *управляет* подом RunPod от вашего имени):

```bash
WEBUI_PASSWORD=<придумайте-пароль> \
WEBUI_BACKEND_IMAGE=ghcr.io/vasilypolyuhovich/witch-avatar-echomimicv3-webui:latest \
ACCOUNT_KEY_FILE=~/.runpod-key-witch-video \
.venv/bin/uvicorn webui.backend.app:app --port 8080
```

Затем откройте `http://localhost:8080`, введите пароль и:

1. Нажмите **Start** — разворачивается под (занимает ~1-2 минуты до
   готовности).
2. Загрузите фото, введите текст, опционально прикрепите короткий
   образец для клонирования голоса.
3. Нажмите **Generate** — WebUI синтезирует речь локально (тот же шаг
   Chatterbox, что и в CLI) и пересылает её поду для рендера. Ожидайте
   **~9-10 минут** для короткого клипа.
4. Нажмите **Stop**, когда закончите — или просто оставьте: у пода есть
   страховочная сеть с 5-минутным таймаутом heartbeat, и он сам
   завершается, если WebUI перестаёт слать heartbeat (браузер закрыт,
   ноутбук уснул и т.д.), так что забытая сессия не может бесконечно
   накручивать расходы.

Страница поддерживает английский и украинский языки (переключение в
шапке).

## Стоимость

- **Время рендера на GPU:** ~$0.05-0.10 за видео на самой дешёвой
  доступной карте ≥40ГБ (обычно NVIDIA A40 по $0.49/час; полный рендер —
  деплой + загрузка модели + генерация + скачивание — занимает ~9-10
  минут).
- **Хранение на сетевом томе:** фиксированная, постоянная стоимость,
  независимая от того, сколько видео вы генерируете — примерно
  $0.07/ГБ/месяц, то есть **~$2/месяц** за том EchoMimicV3 на 30ГБ. Это
  тарифицируется независимо от того, активно ли вы что-то рендерите;
  удалите том через консоль RunPod, если приостанавливаете проект на
  время.
- **Локальный TTS и сам бэкенд WebUI ничего не стоят** — они работают на
  вашей собственной машине.

## Известные ограничения

- **Нужна GPU ≥40ГБ.** Реальный тест на карте 24ГБ (RTX A5000) исчерпал
  память при загрузке модели даже с собственным режимом низкого
  потребления VRAM по умолчанию. Подтверждена работа на 48ГБ (NVIDIA
  A40). Не понижайте `MIN_VRAM` ниже 40 без повторного тестирования.
- **Ограничение ~5.5 секунд на одну генерацию** (138 кадров при 25fps) —
  это собственный документированный лимит EchoMimicV3-Flash для одного
  прохода без режима "Long Video CFG", который этот проект ещё не
  подключил/не проверил. `scripts/run_echomimicv3.sh` и бэкенд WebUI оба
  вычисляют нужное количество кадров из реальной длины вашего аудио и
  **ограничивают его 138 кадрами с громким предупреждением**, а не
  молча производят что-то неправильное — аудио после этой точки будет
  обрезано. Если вам регулярно нужны более длинные клипы, это требует
  доработки (см. `docs/superpowers/plans/` для заметок по Task 11 плана
  миграции).
- **Наличие GPU может быть нестабильным в дата-центре сетевого тома.**
  Сетевой том привязывает каждый деплой к одному конкретному дата-центру
  RunPod (тома не переносимы между дата-центрами), а уровни наличия,
  которые печатает `pod_up.py --dry-run` — это **глобальный** агрегат по
  всем дата-центрам, а не конкретно по тому, где живёт ваш том — GPU
  может показывать наличие "Medium" в целом, реально имея нулевую
  ёмкость именно в вашем привязанном ДЦ. См.
  [Устранение неполадок](#устранение-неполадок) ниже о том, как
  проверить реальное наличие по дата-центру и что с этим делать.
- **Расстановка ударений (наголоси) в русском тексте Chatterbox не
  включена.** Пакет, отвечающий за это (`russian_text_stresser`), не
  поддерживается и, как известно, имеет проблемы установки на
  современном Python; вывод TTS имеет правильное русское произношение
  для однозначных слов, но не различает пары слов, зависящие от
  ударения. Общая интонация/выразительность уже настроена через
  параметры `exaggeration`/`cfg_weight` в
  `scripts/generate_witch_video.py`.
- **Отрендеренное видео не добавляет и не анимирует отдельный фон** —
  EchoMimicV3 генерирует весь кадр из вашего исходного фото; то, какой
  фон уже есть на этом фото, то и появится (с некоторым естественным
  вторичным движением рядом с персонажем — мерцание свечи, ткань — но
  без независимой анимации сцены). Чтобы использовать другой фон,
  отредактируйте исходное фото до генерации, а не после.

## Устранение неполадок

### "supply refused" для каждого кандидата GPU

Список `pod_up.py --dry-run` показывает *глобальное* наличие по всем
дата-центрам RunPod, но деплой с сетевым томом привязан к одному
конкретному дата-центру (тому, где находится том). Список может
показывать наличие "Medium" для GPU, которая реально имеет нулевую
ёмкость именно в вашем дата-центре прямо сейчас. Чтобы проверить
реальное число по конкретному дата-центру, прежде чем предполагать
баг:

```bash
python3 -c "
import json, urllib.request
key = open('~/.runpod-key-witch-video').read().strip()
# реальное наличие по ДЦ, а не глобальный агрегат, который показывает pod_up.py --dry-run
req = urllib.request.Request('https://api.runpod.io/graphql',
  data=json.dumps({'query': '''query{gpuTypes{id lowestPrice(input:{gpuCount:1,secureCloud:true,dataCenterId:\"EU-RO-1\"}){stockStatus}}}'''}).encode(),
  headers={'Authorization': f'Bearer {key}', 'Content-Type':'application/json', 'User-Agent':'x'})
print(json.load(urllib.request.urlopen(req)))
"
```
(замените `EU-RO-1` на дата-центр вашего тома). `stockStatus: null` для
GPU означает реально нулевую ёмкость там прямо сейчас, независимо от
того, что показывает глобальный список. Это может происходить и
происходит — это не специфично для какого-то одного дата-центра.
Повторите попытку через несколько минут или поднимите `--max-price`,
чтобы добраться до более дорогой карты, на которой может остаться
место.

### **Только что созданный** сетевой том проваливает каждый деплой, даже для дешёвых GPU

Замечено напрямую (2026-09-11): сетевой том, которому часы/дни,
деплоится нормально, но том, созданный секунды назад, может провалить
100% попыток деплоя для каждого типа GPU и каждого испробованного
дата-центра, несмотря на то, что те же типы GPU нормально деплоятся в
другом месте. Это похоже на задержку провижининга/распространения на
бэкенде RunPod для только что созданных томов, а не на реальную
проблему с ёмкостью — обходной путь — просто подождать (протестировано:
90 секунд недостаточно; попробуйте несколько минут), прежде чем
доверять отказам деплоя нового тома как "нет в наличии". Если вы
настраиваете сетевой том впервые, не паникуйте, если самая первая
попытка деплоя к нему провалится — повторите попытку после более
долгой паузы, прежде чем делать вывод, что что-то сломано.

### Docker push в GHCR зависает или обрывается на середине локально

Если `docker push` в `ghcr.io` постоянно проваливается с `broken pipe`
или `use of closed network connection` с вашей машины, это чаще всего
нестабильность локальной сети/VM Docker Desktop, а не проблема GHCR —
подтверждено тем, что тот же самый push немедленно проходит успешно из
GitHub Actions. Вместо борьбы с нестабильным локальным соединением,
запустите вместо этого CI-сборку (она пересобирает и пушит на своей
собственной инфраструктуре):

```bash
gh workflow run docker-build-echomimicv3.yml --ref <ваша-ветка>
gh workflow run docker-build-echomimicv3-webui.yml --ref <ваша-ветка>
```

(`workflow_dispatch` требует, чтобы файл workflow YAML уже существовал
на **дефолтной** ветке репозитория, чтобы вообще быть запускаемым — если
вы получаете 404 "workflow not found", файл сначала нужно смержить туда,
даже если вы хотите собрать Dockerfile из другой ветки через `--ref`.)

Если сам CI проваливается с `permission_denied: write_package`,
настройки репозитория Settings → Actions → General → Workflow
permissions, вероятно, установлены только на "Read repository contents
permission" — исправляется так:
```bash
gh api -X PUT repos/<owner>/<repo>/actions/permissions/workflow \
  -f default_workflow_permissions=write -F can_approve_pull_request_reviews=false
```
Если вместо этого при повторной попытке сразу после этого исправления
возникает `permission_denied: read_package`, предыдущий провалившийся
запуск, вероятно, оставил пакет GHCR в сломанном промежуточном
состоянии — удалите его полностью
(`gh api -X DELETE /user/packages/container/<name>`) и дайте CI создать
его заново с чистого листа при следующем запуске. Проверяйте, что любой
"успешный" push реально произвёл настоящий, скачиваемый образ, с
помощью `docker manifest inspect ghcr.io/<owner>/<image>:latest` — было
замечено, что и сообщение об успехе запуска CI, и наличие пакета в
списке пакетов GHCR могут независимо друг от друга врать об этом.

## Структура репозитория

| Путь | Что это |
|---|---|
| `scripts/generate_witch_video.py` | Точка входа CLI |
| `scripts/pod_up.py` | Примитивы деплоя/ранжирования/завершения GPU RunPod, общие для обоих способов запуска |
| `scripts/run_echomimicv3.sh` | Выполняется на поде для CLI-пути; оборачивает скрипт инференса EchoMimicV3 |
| `scripts/populate_echomimicv3_volume.sh` | Одноразовая загрузка весов на сетевой том (см. [настройку](#3-настройка-сетевого-тома-одноразово-24гб-весов-модели)) |
| `docker/echomimicv3/` | Образ пода для CLI-пути (только SSH, без HTTP-сервера) |
| `docker/echomimicv3-webui/` | Образ пода для WebUI-пути (небольшой HTTP API: `/health`, `/generate`, `/status`, `/result`) |
| `docker/webui-stub/` | Одноразовый фейковый бэкенд (заранее записанный тестовый клип, без реального GPU-инференса), использовавшийся для сборки/тестирования HTTP-механики WebUI до появления реального бэкенда — оставлен для справки, не часть реального пайплайна |
| `webui/backend/` | Локальный FastAPI-сервер, который вы запускаете сами; управляет подом `docker/echomimicv3-webui` через HTTP |
| `webui/frontend/` | Статическая страница, которую отдаёт `webui/backend` |
| `tests/` | Набор тестов pytest (`./.venv/bin/python -m pytest tests/`) |
| `docs/2026-08-13-witch-avatar-video-design.md` | Изначальная проектная спецификация |
| `docs/decisions.md` | Журнал эмпирических находок, пополняется по мере обнаружения |
