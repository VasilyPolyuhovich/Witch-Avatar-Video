# Witch Avatar Video

*Readme також доступний: [English](README.md) | [Русский](README.ru.md)*

Генерує короткі (5-15с) відео-флаєри "говорячої голови" вигаданого
персонажа — відьми/ворожки — для Instagram, з референсного фото та рядка
російського тексту: локальний синтез мовлення, потім GPU-под за
потребою рендерить відео з синхронізацією губ і сам себе завершує.

Повне обґрунтування дизайну: [`docs/2026-08-13-witch-avatar-video-design.md`](docs/2026-08-13-witch-avatar-video-design.md).
Журнал емпіричних знахідок/рішень: [`docs/decisions.md`](docs/decisions.md).

## Як це працює

1. **Синтез мовлення виконується локально**, на вашій машині — [Chatterbox
   Multilingual TTS](https://github.com/resemble-ai/chatterbox) перетворює
   ваш текст на `.wav`, опційно клонуючи голос із короткого референсного
   зразка. На цьому етапі GPU-под ще не існує, тому невдалий текст або
   референсний кліп нічого не коштують.
2. **GPU-под розгортається на RunPod за потребою** ([EchoMimicV3-Flash](https://github.com/antgroup/echomimic_v3),
   дифузійна модель на основі Wan2.1-Fun), рендерить фото+аудіо у відео,
   і под **завжди завершується після цього** — при успіху, помилці чи
   Ctrl-C — тож нічого ніколи не залишається працювати й тарифікуватись
   випадково.
3. **Два незалежні способи запуску**, обидва звертаються до тих самих
   образів пода:
   - `scripts/generate_witch_video.py` — CLI-скрипт, запустіть його і
     отримайте `.mp4` назад.
   - **WebUI** (`webui/`) — невелика захищена паролем локальна
     веб-сторінка (ввести текст, завантажити фото, натиснути Generate)
     для нетехнічного використання.

## Попередні вимоги

- **Python 3.10+** локально (розроблено/протестовано на Apple Silicon,
  macOS).
- **Акаунт RunPod** із налаштованим білінгом ([runpod.io](https://runpod.io)) —
  саме він реально виконує GPU-рендер. Типова вартість: **~$0.05-0.10 за
  одне згенероване відео** (див. [Вартість](#вартість) нижче).
- **`ffmpeg`**, встановлений локально (`brew install ffmpeg` на macOS) —
  використовується для постобробки TTS-аудіо.
- **Docker**, лише якщо вам колись знадобиться перезібрати образи пода
  самостійно (не потрібно для щоденного використання — образи вже
  зібрані й опубліковані в GHCR через CI).

## Одноразове налаштування

### 1. Клонування та встановлення

```bash
git clone <this-repo-url>
cd Witch-Avatar-Video
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

**Відома локальна проблема:** залежність `chatterbox-tts` для водяних
знаків (`resemble-perth`) потребує застарілого модуля `pkg_resources`,
який сучасний `setuptools` (приблизно від версії 76) більше не постачає.
Якщо ви бачите `TypeError: 'NoneType' object is not callable` зсередини
Chatterbox, виконайте:

```bash
.venv/bin/pip install "setuptools==75.8.0"
```

(pip виведе попередження резолвера про те, що `torch` хоче новіший
`setuptools` — це лише попередження, не реальний конфлікт; torch працює
нормально.) Дивіться `docs/decisions.md` / пам'ять проєкту за повною
історією, якщо це продовжує повторюватись.

### 2. Отримання API-ключа RunPod та пари SSH-ключів

1. Створіть API-ключ на [runpod.io/console/user/settings](https://www.runpod.io/console/user/settings)
   і збережіть його в `~/.runpod-key-witch-video` (звичайний текстовий
   файл, лише сам ключ, без лапок/проблем із переносом рядка).
2. Згенеруйте пару SSH-ключів, якій довірятимуть поди RunPod:
   ```bash
   mkdir -p ~/.runpod/ssh
   ssh-keygen -t rsa -b 4096 -f ~/.runpod/ssh/runpodctl-witch-video-ssh-key -N ""
   ```
   (`scripts/pod_up.py` за замовчуванням читає ці два шляхи —
   перевизначте через змінні середовища `ACCOUNT_KEY_FILE` /
   `SSH_PUBKEY_FILE` / `SSH_PRIVKEY_FILE`, якщо зберігаєте їх в іншому
   місці.)

### 3. Налаштування мережевого тому (одноразово, ~24ГБ ваг моделі)

Ваги EchoMimicV3 (~24ГБ) живуть на **мережевому томі** RunPod, а не
запечені в образ пода — том, будучи одного разу заповненим,
перевикористовується кожним наступним рендером без повторного
завантаження чогось.

1. Створіть мережевий том на 30ГБ через консоль RunPod (Storage →
   Network Volumes) у дата-центрі з реальною (а не лише глобально
   вказаною) наявністю карт ≥40ГБ — див. [Усунення несправностей](#усунення-несправностей)
   нижче про те, як перевірити реальну наявність по конкретному
   дата-центру перед вибором, оскільки стандартне відображення
   ранжування GPU — це глобальний агрегат, який може вводити в оману
   для деплою, прив'язаного до тому. Запишіть id тому. Дайте щойно
   створеному тому кілька хвилин, перш ніж довіряти будь-яким відмовам
   деплою як "немає в наявності" — див. Усунення несправностей.
2. Розгорніть дешевий тимчасовий под із цим томом, підключеним у
   `/workspace` (підійде будь-яка невелика GPU — цьому кроку не
   потрібні реальні обчислення, лише змонтований том):
   ```bash
   NETWORK_VOLUME_ID=<ваш-id-тому> MIN_VRAM=8 MAX_PRICE=0.2 \
     .venv/bin/python3 scripts/pod_up.py
   ```
3. Підключіться по SSH до цього пода (команда виводить рядок SSH),
   завантажте й запустіть скрипт заповнення, потім завершіть под:
   ```bash
   scp -P <port> -i ~/.runpod/ssh/runpodctl-witch-video-ssh-key \
     scripts/populate_echomimicv3_volume.sh root@<ip>:/root/
   ssh -p <port> -i ~/.runpod/ssh/runpodctl-witch-video-ssh-key root@<ip> \
     "chmod +x /root/populate_echomimicv3_volume.sh && /root/populate_echomimicv3_volume.sh"
   ```
   Очікуйте завантаження ~24ГБ, яке займе кілька хвилин. Скрипт
   перевіряє SHA256 кожного завантаженого pickle-чекпоінта перед
   завершенням.
4. Завершіть тимчасовий под (через консоль RunPod або `podTerminate`
   через API) — не залишайте його працювати.
5. Встановіть `DEFAULT_NETWORK_VOLUME_ID` у `scripts/pod_up.py` в id
   вашого тому (або експортуйте `NETWORK_VOLUME_ID` при кожному запуску
   скрипта замість жорсткого прописування).

Це потрібно зробити лише один раз. Самі образи (`witch-avatar-echomimicv3`
і `witch-avatar-echomimicv3-webui`) вже публічні в GHCR і автоматично
перезбираються через CI при кожній зміні в `docker/echomimicv3*/` —
ручна збірка Docker не потрібна для звичайного використання.

## Використання

### CLI

```bash
.venv/bin/python3 scripts/generate_witch_video.py \
  --image assets/gadalka_portrait.jpg \
  --text "Добро пожаловать, дитя моё. Огонь свечи откроет тебе то, что скрыто во тьме." \
  --voice-sample assets/gadalka-voice-reference.wav \
  --output outputs/flyer.mp4
```

- `--voice-sample` опційний — пропустіть його, щоб використати вбудований
  голос Chatterbox за замовчуванням замість клонування.
- `--dry-run` ранжує доступні GPU і друкує, що сталося б — без виклику
  TTS, без деплою, без витрат. Використовуйте це для перевірки
  цін/наявності GPU перед реальним запуском.
- `--tts-only` генерує лише локальний аудіофайл і зупиняється — корисно
  для попереднього прослуховування тексту перед витратою грошей на под.
- `--max-price` / `--min-vram` перевизначають пошук GPU (значення за
  замовчуванням: мінімум 40ГБ, стеля $0.60/год — див.
  [Відомі обмеження](#відомі-обмеження)).
- Повний список флагів: `--help`.

Под **завжди** завершується в блоці `finally`, включно з Ctrl-C чи збоєм
посеред рендеру — вам ніколи не повинно знадобитись вручну прибирати за
подом після CLI-запуску.

### WebUI

Запустіть локальний бекенд (він працює на вашій власній машині, не на
RunPod — саме він *керує* подом RunPod від вашого імені):

```bash
WEBUI_PASSWORD=<придумайте-пароль> \
WEBUI_BACKEND_IMAGE=ghcr.io/vasilypolyuhovich/witch-avatar-echomimicv3-webui:latest \
ACCOUNT_KEY_FILE=~/.runpod-key-witch-video \
.venv/bin/uvicorn webui.backend.app:app --port 8080
```

Потім відкрийте `http://localhost:8080`, введіть пароль і:

1. Натисніть **Start** — розгортається под (займає ~1-2 хвилини до
   готовності).
2. Завантажте фото, введіть текст, опційно прикріпіть короткий зразок
   для клонування голосу.
3. Натисніть **Generate** — WebUI синтезує мовлення локально (той самий
   крок Chatterbox, що і в CLI) і пересилає його поду для рендеру.
   Очікуйте **~9-10 хвилин** для короткого кліпу.
4. Натисніть **Stop**, коли закінчите — або просто залиште: у пода є
   страхувальна сітка з 5-хвилинним тайм-аутом heartbeat, і він сам
   завершується, якщо WebUI перестає надсилати heartbeat (браузер
   закрито, ноутбук заснув тощо), тож забута сесія не може нескінченно
   накручувати витрати.

Сторінка підтримує англійську та українську мови (перемикання в шапці).

## Вартість

- **Час рендеру на GPU:** ~$0.05-0.10 за відео на найдешевшій доступній
  карті ≥40ГБ (зазвичай NVIDIA A40 за $0.49/год; повний рендер — деплой
  + завантаження моделі + генерація + скачування — займає ~9-10
  хвилин).
- **Зберігання на мережевому томі:** фіксована, постійна вартість,
  незалежна від того, скільки відео ви генеруєте — приблизно
  $0.07/ГБ/місяць, тобто **~$2/місяць** за том EchoMimicV3 на 30ГБ. Це
  тарифікується незалежно від того, чи активно ви щось рендерите;
  видаліть том через консоль RunPod, якщо призупиняєте проєкт на
  якийсь час.
- **Локальний TTS і сам бекенд WebUI нічого не коштують** — вони
  працюють на вашій власній машині.

## Відомі обмеження

- **Потрібна GPU ≥40ГБ.** Реальний тест на карті 24ГБ (RTX A5000)
  вичерпав пам'ять під час завантаження моделі навіть із власним
  режимом низького споживання VRAM за замовчуванням. Підтверджена
  робота на 48ГБ (NVIDIA A40). Не знижуйте `MIN_VRAM` нижче 40 без
  повторного тестування.
- **Обмеження ~5.5 секунд на одну генерацію** (138 кадрів при 25fps) —
  це власний задокументований ліміт EchoMimicV3-Flash для одного
  проходу без режиму "Long Video CFG", який цей проєкт ще не
  підключив/не перевірив. `scripts/run_echomimicv3.sh` і бекенд WebUI
  обидва обчислюють потрібну кількість кадрів із реальної довжини
  вашого аудіо і **обмежують її 138 кадрами з гучним попередженням**, а
  не мовчки виробляють щось неправильне — аудіо після цієї точки буде
  обрізане. Якщо вам регулярно потрібні довші кліпи, це потребує
  доопрацювання (див. `docs/superpowers/plans/` для нотаток по Task 11
  плану міграції).
- **Наявність GPU може бути нестабільною в дата-центрі мережевого
  тому.** Мережевий том прив'язує кожен деплой до одного конкретного
  дата-центру RunPod (томи не переносяться між дата-центрами), а рівні
  наявності, які друкує `pod_up.py --dry-run` — це **глобальний**
  агрегат по всіх дата-центрах, а не конкретно по тому, де живе ваш
  том — GPU може показувати наявність "Medium" загалом, реально маючи
  нульову ємність саме у вашому прив'язаному ДЦ. Див.
  [Усунення несправностей](#усунення-несправностей) нижче про те, як
  перевірити реальну наявність по дата-центру і що з цим робити.
- **Розстановка наголосів у російському тексті Chatterbox не
  увімкнена.** Пакет, що за це відповідає (`russian_text_stresser`), не
  підтримується і, як відомо, має проблеми встановлення на сучасному
  Python; вивід TTS має правильну російську вимову для однозначних
  слів, але не розрізняє пари слів, залежні від наголосу. Загальна
  інтонація/виразність вже налаштована через параметри
  `exaggeration`/`cfg_weight` у `scripts/generate_witch_video.py`.
- **Відрендерене відео не додає і не анімує окремий фон** — EchoMimicV3
  генерує весь кадр із вашого вихідного фото; який фон вже є на цьому
  фото, той і з'явиться (з деяким природним вторинним рухом поруч із
  персонажем — мерехтіння свічки, тканина — але без незалежної анімації
  сцени). Щоб використати інший фон, відредагуйте вихідне фото до
  генерації, а не після.

## Усунення несправностей

### "supply refused" для кожного кандидата GPU

Список `pod_up.py --dry-run` показує *глобальну* наявність по всіх
дата-центрах RunPod, але деплой із мережевим томом прив'язаний до
одного конкретного дата-центру (того, де знаходиться том). Список може
показувати наявність "Medium" для GPU, яка реально має нульову ємність
саме у вашому дата-центрі прямо зараз. Щоб перевірити реальне число по
конкретному дата-центру, перш ніж припускати баг:

```bash
python3 -c "
import json, urllib.request
key = open('~/.runpod-key-witch-video').read().strip()
# реальна наявність по ДЦ, а не глобальний агрегат, який показує pod_up.py --dry-run
req = urllib.request.Request('https://api.runpod.io/graphql',
  data=json.dumps({'query': '''query{gpuTypes{id lowestPrice(input:{gpuCount:1,secureCloud:true,dataCenterId:\"EU-RO-1\"}){stockStatus}}}'''}).encode(),
  headers={'Authorization': f'Bearer {key}', 'Content-Type':'application/json', 'User-Agent':'x'})
print(json.load(urllib.request.urlopen(req)))
"
```
(замініть `EU-RO-1` на дата-центр вашого тому). `stockStatus: null` для
GPU означає реально нульову ємність там прямо зараз, незалежно від
того, що показує глобальний список. Це може траплятись і трапляється —
це не специфічно для якогось одного дата-центру. Повторіть спробу через
кілька хвилин або підійміть `--max-price`, щоб дістатись дорожчої
карти, на якій може залишитись місце.

### **Щойно створений** мережевий том провалює кожен деплой, навіть для дешевих GPU

Помічено напряму (2026-09-11): мережевий том, якому години/дні,
деплоїться нормально, але том, створений секунди тому, може провалити
100% спроб деплою для кожного типу GPU й кожного випробуваного
дата-центру, попри те що ті самі типи GPU нормально деплояться в
іншому місці. Це схоже на затримку провіжинінгу/поширення на бекенді
RunPod для щойно створених томів, а не на реальну проблему з ємністю —
обхідний шлях — просто зачекати (протестовано: 90 секунд недостатньо;
спробуйте кілька хвилин), перш ніж довіряти відмовам деплою нового тому
як "немає в наявності". Якщо ви налаштовуєте мережевий том вперше, не
панікуйте, якщо найперша спроба деплою до нього провалиться —
повторіть спробу після довшої паузи, перш ніж робити висновок, що
щось зламано.

### Docker push у GHCR зависає або обривається на середині локально

Якщо `docker push` у `ghcr.io` постійно провалюється з `broken pipe` чи
`use of closed network connection` з вашої машини, це найчастіше
нестабільність локальної мережі/VM Docker Desktop, а не проблема GHCR —
підтверджено тим, що той самий push негайно проходить успішно з GitHub
Actions. Замість боротьби з нестабільним локальним з'єднанням, запустіть
натомість CI-збірку (вона перезбирає й пушить на своїй власній
інфраструктурі):

```bash
gh workflow run docker-build-echomimicv3.yml --ref <ваша-гілка>
gh workflow run docker-build-echomimicv3-webui.yml --ref <ваша-гілка>
```

(`workflow_dispatch` вимагає, щоб файл workflow YAML вже існував на
**дефолтній** гілці репозиторію, щоб взагалі бути запускним — якщо ви
отримуєте 404 "workflow not found", файл спочатку потрібно змержити
туди, навіть якщо ви хочете зібрати Dockerfile з іншої гілки через
`--ref`.)

Якщо сам CI провалюється з `permission_denied: write_package`,
налаштування репозиторію Settings → Actions → General → Workflow
permissions, ймовірно, встановлені лише на "Read repository contents
permission" — виправляється так:
```bash
gh api -X PUT repos/<owner>/<repo>/actions/permissions/workflow \
  -f default_workflow_permissions=write -F can_approve_pull_request_reviews=false
```
Якщо натомість при повторній спробі одразу після цього виправлення
виникає `permission_denied: read_package`, попередній провалений запуск,
ймовірно, залишив пакет GHCR у зламаному проміжному стані — видаліть
його повністю (`gh api -X DELETE /user/packages/container/<name>`) і
дайте CI створити його заново з чистого аркуша при наступному запуску.
Перевіряйте, що будь-який "успішний" push реально виробив справжній,
завантажуваний образ, за допомогою
`docker manifest inspect ghcr.io/<owner>/<image>:latest` — було помічено,
що і повідомлення про успіх запуску CI, і наявність пакета в списку
пакетів GHCR можуть незалежно одне від одного брехати про це.

## Структура репозиторію

| Шлях | Що це |
|---|---|
| `scripts/generate_witch_video.py` | Точка входу CLI |
| `scripts/pod_up.py` | Примітиви деплою/ранжування/завершення GPU RunPod, спільні для обох способів запуску |
| `scripts/run_echomimicv3.sh` | Виконується на поді для CLI-шляху; обгортає скрипт інференсу EchoMimicV3 |
| `scripts/populate_echomimicv3_volume.sh` | Одноразове завантаження ваг на мережевий том (див. [налаштування](#3-налаштування-мережевого-тому-одноразово-24гб-ваг-моделі)) |
| `docker/echomimicv3/` | Образ пода для CLI-шляху (лише SSH, без HTTP-сервера) |
| `docker/echomimicv3-webui/` | Образ пода для WebUI-шляху (невеликий HTTP API: `/health`, `/generate`, `/status`, `/result`) |
| `docker/webui-stub/` | Одноразовий фейковий бекенд (заздалегідь записаний тестовий кліп, без реального GPU-інференсу), що використовувався для збірки/тестування HTTP-механіки WebUI до появи реального бекенду — залишений для довідки, не частина реального пайплайну |
| `webui/backend/` | Локальний FastAPI-сервер, який ви запускаєте самі; керує подом `docker/echomimicv3-webui` через HTTP |
| `webui/frontend/` | Статична сторінка, яку віддає `webui/backend` |
| `tests/` | Набір тестів pytest (`./.venv/bin/python -m pytest tests/`) |
| `docs/2026-08-13-witch-avatar-video-design.md` | Початкова проєктна специфікація |
| `docs/decisions.md` | Журнал емпіричних знахідок, поповнюється по мірі виявлення |
